# Decision log (ADR-style)

Decisions made on 2026-10-30 after the owner delegated them ("proceed with your best recommendations"). Each lists the evidence, the alternative rejected, and what would reverse it. Reversible unless noted.

| # | Decision | Why | Rejected / revisit trigger |
|---|---|---|---|
| D1 | **Apache-2.0 for the engine crates** (`plinth-core`, `plinth-host`, demos); the store backend, curation and any Plus features stay proprietary | The trust claim (permission broker, sandbox rules) is only credible if auditable; the business is curation, store and creator tools, not the broker. Apache-2.0 includes a patent grant and is easy for contributors and companies. No AGPL/GPL code is copied in (Seelen UI and Lively are copyleft). | AGPL (would deter contributors, no benefit as we sell no hosted code); closed source (weakens the trust story). Revisit if a competitor forks and out-markets us. `LICENSE` added from apache.org. |
| D2 | **Public name unresolved; "Plinth" is a codename only** and is high risk | Search found: FreedomBox's web interface called Plinth, a Flutter UI library "Plinth UI", an iOS app "Plinth", and an Australian PLINTH trademark application covering SaaS/web software (still in opposition at search time). No US/EU register was checked. | Do not publish under "Plinth". Shortlist 3 coined names and run a real clearance (USPTO, EUIPO, WIPO, app stores, domains) before any public page; keep crate names until then. |
| D3 | **Primary users: casual-aesthetic Windows users and streamers; creators second; power users third** | Consumer research (setup-sharing culture, widgets-on-desktop demand, cost anxiety) points here; power users already have Rainmeter 5.0 and Seelen UI. | Revisit after 15 interviews and the waitlist test. |
| D4 | **Payments: merchant-of-record provider at v1.0**, not our own Stripe Connect integration | A solo developer should not carry VAT/sales-tax, KYC and refunds. Provider fees are UNVERIFIED and must be compared (Paddle, Lemon Squeezy, others) before choosing. | Build direct payouts only after volume justifies it. |
| D5 | **Distribution: signed installer + winget + Microsoft Store**, auto-update with rollback | Matches how Windows users discover tools (Seelen UI uses all three). Code-signing certificate is a paid prerequisite; consider the signing service route used by open-source projects. | Store-only would lose users without Store access. |
| D6 | **Stack stays Rust core + WebView2 host + Svelte hub** | Spikes show the WebView2 route survives Win+D and costs about 146 MB fixed + about 29 MB per isolated widget; native Direct2D remains the fallback for first-party widgets if low-end hardware proves it necessary. | Revisit after low-end hardware and multi-monitor measurements. |
| D7 | **Widget delivery: hybrid.** Bundled first-party widgets share one trusted origin; each third-party widget gets its own origin via custom protocol, header CSP, host `frame-src` allowlist; cap about 8 concurrent third-party widgets per monitor | Spike C: srcdoc iframes leaked network and let a busy loop freeze everything; per-origin delivery blocked all tested HTTP channels and contained the hog. | Cap is a guess; measure on low-end PCs. |
| D8 | **All widget network traffic goes through a Plinth-controlled local proxy; widgets never reach the network directly** (implemented in `plinth-proxy`, validated in host-demo) | host-demo: a widget's self-navigation opened a bare TCP connection even under CSP (a destination-address leak, possible DNS covert channel); forcing WebView2 through a local proxy produced 0 direct connections in 4 of 4 runs. The proxy also enables allow-listing, audit log, rate limits and Impact Meter data. | Per-widget attribution at the proxy is unsolved (see `apps/host-demo/RESULTS.md`); per-widget WebView2 profiles are too heavy. |
| D9 | **Telemetry opt-in only; no account required for the free core** | Trust product; consumer privacy expectations. | n/a |
| D10 | **Pitch**: "Make it yours, share it in one click, keep it cheap on your PC, and know it is safe" | `research/consumer-demand.md`. | Test the "post your setup card" loop with a waitlist page. |
| D11 | **Setup Cards are code-free and validated; remix credit chain recorded** | Creators get credit; users get a safe unit to share; limits parsing risk. | Signing of cards deferred to v1.0 store. |
| D12 | **Release cadence**: minor version per completed milestone, tag on `main`, spike/feature branches, CI on every push | `CONTRIBUTING.md`. | n/a |
| D13 | **App shell: `wry` + `tao` (the layer Tauri is built on), plain HTML/JS hub, no Node toolchain** | The spikes already proved wry+tao on this machine; full Tauri adds a large dependency tree and a JS build step for no capability we use yet; the hub is small and the prototype is vanilla JS. Fewer dependencies also means a smaller attack and memory surface. | Revisit (Tauri + Svelte) if hub complexity or plugin needs grow. |
| D14 | **Built-in widgets are granted their declared permissions at first run; third-party widgets start with nothing** | Matches the first-run promise ("Allowed / Asks / Never") and keeps the first 10 minutes frictionless. | Safe mode currently pauses first-party widgets too; add an exemption if users find that annoying. |
| D15 | **Project working method adopted from the harness infographic**: lean `CLAUDE.md`, `feature_list.json` with evidence, `claude-progress.md`, one-command `scripts/verify.ps1`, skills on demand | Durable state lets sessions resume after context loss; deterministic checks beat model judgment. The infographic is a social-media summary of Anthropic guidance (UNVERIFIED against the primary docs); only the ideas, not its numbers, were used. | n/a |
| D16 | **Beachhead audience: PC builders and enthusiasts** (hardware vitals, build showcase, case/secondary screens, live wallpapers), with the same Scenes serving casual users | Large, vocal communities that show off setups (r/pcmasterrace about 15.9M, r/buildapc about 8.3M, r/battlestations about 5.2M; weak, stale counts); pain with RGB suite conflicts and driver-based monitoring; they care about performance and safety. Willingness to pay UNVERIFIED. | Validate with the waitlist and interviews; drop if builders neither pay nor share. |
| D17 | **No kernel driver of our own.** Use user-mode sources (GetSystemTimes, PDH counters, NVML, registry); label unavailable sensors honestly (CPU temperature and fans are not available in user mode on the tested PC); optional bridges to tools the user runs | WinRing0 is flagged by Defender (CVE-2020-14979); a driver would also contradict the safety pitch. | Revisit if signed PawnIO-style modules become an accepted, redistributable path; avoid the HWiNFO shared-memory interface in open-source code (license terms, 12 h limit in the free version). |
| D18 | **RGB via the OpenRGB SDK server as a client, optional and later** | Avoids reimplementing vendor protocols and vendor-suite conflicts; a separate process keeps GPL-2.0-or-later code out of our Apache-2.0 crates. Protocol details UNVERIFIED. | Have a lawyer check license interplay before bundling anything. |
| D19 | **Output targets are first-class**: a Scene or widget layout can target a chosen monitor, including secondary/case screens | Case screens are driven by dashboards today. NOT TESTED on multiple monitors. | n/a |
| D20 | **Skills/plugins policy**: official repos (`anthropics/skills`, `anthropics/claude-plugins-official`) and built-in `/security-review`; community lists for discovery only; read a skill's files before use; never auto-install; third-party skill text is untrusted instructions | Skills can direct Claude to run code and touch files; official READMEs say to trust plugins before installing. | n/a |
| D21 | **First-party widgets share one trusted origin and one process; third-party widgets keep isolated origins** | Implements the hybrid in D7; saves roughly 29 MB per first-party widget (Spike C cost). Identity is decided by the trusted layer page per iframe, never by the widget. | Measure the saving; split origins if first-party widgets ever need isolation from each other. |
| D22 | **Product scope: one app, three pillars on one safe runtime: live motion wallpapers, system monitoring, security** (owner's vision, 2026-10-30). Security means (a) the sandbox, permissions and proxy and (b) a Security Center of visibility (Windows security status, per-process network connections, startup items, Plinth's own blocked-attempt log). It is NOT an antivirus and must never claim malware detection | The three tools are separate products today; a single sandboxed runtime lets them share one sampler, one pause governor and one trust model. | Re-scope if the Security Center cannot be built honestly in user mode (NOT TESTED yet). |
| D23 | **Wallpapers are a separate, permissionless content type: video files and sandboxed web pages, served from their own origin (`pwv.localhost`)** | A wallpaper only needs to draw, so it gets no bridge, no permissions and no network. Video is passive data played by the trusted layer page; a web wallpaper runs in an `allow-scripts` iframe without `allow-same-origin` (opaque origin) under a CSP with `connect-src 'none'`. Folders are validated (closed id, entry and file-type allow-lists, no path escape, symlinks resolved) and only the user's own copy of an imported video is ever removed. Wallpaper Engine's Workshop had to close a category after a malware problem (research/pc-builders.md, single weak source), so the safe default is a locked box. | Revisit if creators need audio-reactive wallpapers (would need a narrow, granted `audio.levels` permission, not a general bridge). Per-monitor targeting is not built (NOT TESTED on multiple monitors). |
| D24 | **Static image wallpapers: set through the OS (`IDesktopWallpaper`) AND drawn in the layer on monitors that have widgets** | The OS path costs nothing at runtime, survives Plinth quitting or crashing, and gives per-monitor images and native fit modes (Fill, Fit, Stretch, Tile, Span, Center) [S42-S44]. Widgets use frosted glass (`backdrop-filter`), which needs the picture inside the layer page, so monitors with widgets also draw the image in the layer; monitors without widgets need no layer (zero cost). Native slideshow only accepts one folder [S45], so Plinth runs its own rotation timer. Revert restores a per-monitor snapshot of the previous OS wallpaper, position and color. Adds the official `windows` crate for COM (raw vtables are error-prone). | If a transparent layer proves viable (not tested) the duplicate drawing can go. |
| D25 | **Monitor identity: `monitorDevicePath` from `DisplayConfigGetDeviceInfo`, with an EDID fingerprint (manufacturer, product code, connector instance) as fallback and screen position as last resort** | Indices change on plug/unplug (Rainmeter users hit this [S52]); the device path and EDID ids are the documented stable-ish identifiers [S48, S49]. Shared setups strip hardware ids and use roles (primary, second from left...). Stability across docks and port swaps is NOT TESTED (one monitor here). | Revisit after testing on real multi-monitor hardware. |
| D26 | **Widget placement is stored per monitor as an anchor plus offsets and sizes in device-independent units, and a pure function `reconcile(saved, connected monitors)` computes where everything shows; transient states are never written back** | The documented Rainmeter failure is exactly "wrong positions during a display change get autosaved over the good ones" [S52]. Saving only each widget's `home` assignment, never the parked or clamped result, makes unplug/replug lossless by construction. | None; this is an invariant with tests. |
| D27 | **Layer topology: one layer window per monitor that needs one (widgets or a motion wallpaper), sharing one WebView2 environment** | Mixed-DPI monitors need separate windows; a single spanning window has one DPI. Memory of the second and third layer is NOT MEASURED (the first costs about 270 MB); measure before promising numbers, and cap motion wallpapers at one active by default with the Impact Meter showing the total. | If the cost is too high, fall back to one layer on the monitor with widgets and static OS wallpapers elsewhere. |
| D28 | **Wallpaper library: SQLite index (WAL) + on-disk thumbnail cache keyed by content hash + virtualized grid; folders watched with `ReadDirectoryChangesW`-based watching plus polling for network/USB folders; offline folders keep their items marked offline** | Scales to 10,000+ images with a small, bounded memory cost; renames are detected by file id or content hash instead of a full rescan; unplugging a drive never deletes library entries. Details and budgets in `architecture.md` section 12. | Revisit the database choice if the C dependency is a build problem. |
| D29 | **Animated wallpapers stay in MVP (shipped in v0.8.0), reversing the addendum's default of v1.0** | The addendum said to keep animated wallpapers out of MVP unless research proves otherwise. Measured: a 1080p video costs +90 MB and +2.6% of one core while visible, about 0% when covered; web wallpapers +2.6 to +7.2% (CHANGELOG 0.8.0). They reuse the same layer and governor, and they are the headline for the PC-builder audience. Cost is shown in the Impact Meter, motion is opt-in per wallpaper, and only one motion wallpaper is active by default. GPU load was not measured. | Revisit if GPU load measurements are bad. |
| D30 | **Security Center is read-only visibility built from user-mode facts: firewall switches, antivirus/Defender status as Windows reports it, TCP connections and listeners per program, startup items; it never claims to detect malware** | The audience (PC builders, D16) wants to see what their PC is doing; an antivirus claim would be unprovable and dangerous. Sources: policy registry values, Windows Security Center via one fixed PowerShell command (no user input is interpolated, absolute path, 20 s timeout, no window), `GetExtendedTcpTable`, Run keys and Startup folders. The `productState` bit decode is community-documented (UNVERIFIED). On-demand only, no background cost. Process names and commands are untrusted text and are escaped in the hub (regression check extended). | Scheduled tasks, services, per-connection bytes, DNS names, file signatures and an unknown-publisher heuristic are NOT covered (would need more APIs or a driver, D17). |
| D31 | **As built: Plinth composes each monitor's picture itself (fit mode, bars color, span slice) and the OS only shows a monitor-sized bitmap** | The OS fit position and background color look global in the interface [S44]; composing gives a different fit per monitor, exact Span, and a picture the layer can draw identically. JPEG quality 92, cached by name, at most 24 files kept. Verified end to end on the real monitors: the OS reported the composed file as the wallpaper of the chosen monitor and Revert restored both monitors exactly (autotest, 10 of 10). | If a user wants the OS's own behavior (picture follows resolution changes by itself), add a "let Windows fit it" option. |
| D32 | **As built: the library index is a JSON file, not SQLite (amends D28)** | Measured with 10,003 pictures: save 22 ms (3.2 MB), load 28 ms, a grid page 3.4 ms, search 2.3 ms, unchanged rescan 18 ms. That is well inside the budget, and it avoids a C dependency. Revisit above about 100,000 pictures or if queries get richer. Directory-change notifications are not used yet: the watcher rescans every 5 s while the hub is open and every 60 s otherwise (an unchanged rescan costs 18 ms). | SQLite or ReadDirectoryChangesW if scale or battery cost demands it. |
| D33 | **Verified facts and one real bug from two-monitor testing (2026-10-30)** | This PC has two monitors (1920x1080 primary and a 1280x400 case screen at negative coordinates), not one as earlier notes said. (1) The shell's monitor ids from `IDesktopWallpaper` are identical to the DisplayConfig device paths on both monitors, so the join D25 wanted holds here (FACT for this PC). (2) Reading the real window rectangles showed the layer inset by about 8 px since v0.5; fixed. (3) A second layer costs +41 MB. | Still NOT TESTED: dock/undock, port swap, two identical monitors, mixed DPI, virtual desktops. |
